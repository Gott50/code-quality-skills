# Prototype notes — the applied-state manifest

Throwaway. Branch `prototype/manifest`, off `main`, never merged, no PR. This is the primary source
for wayfinder ticket **Applied-state manifest: schema, idempotency proof, and the update path**; the
decision it settles lives in that ticket's resolution comment.

## What the prototype is

| Artifact | Path |
|---|---|
| The logic (liftable) | `prototype/manifest.mjs` |
| The shareable demo (HITL) | `prototype/manifest-demo.html`, generated by `prototype/build-demo.mjs` from `prototype/demo-shell.html` |
| The real fixture run | `prototype/manifest-transcript.mjs` → `prototype/manifest-transcript.txt` |

`manifest.mjs` is pure: no fs, no DOM, no network, no dependencies. Two worlds drive it — the demo's
in-memory world and the transcript's scratch directory — so the state model is exercised twice
against two different filesystems. The demo is one self-contained file (the module is inlined by
`build-demo.mjs`, because a `file://` page cannot `import` a sibling module); the transcript imports
the module directly.

## The schema — `.code-quality.json`

```jsonc
{
  "schemaVersion": 1,
  "skill": { "name": "code-quality-setup", "version": "0.1.0" },
  "appliedAt": "2026-10-08T19:30:00.000Z",
  "environment": {
    "packageManager": "bun",
    "workspace": "single",
    "languages": ["typescript"]
  },
  "recipes": [
    {
      "id": "biome-assist",
      "skillVersion": "0.1.0",
      "recipeHash": "a1b2c3d4",
      "appliedAt": "2026-10-08T19:30:00.000Z",
      "files": [
        { "path": "biome.json", "action": "create", "hash": "0f1e2d3c" },
        { "path": ".husky/pre-commit", "action": "merge", "hash": "9a8b7c6d" }
      ]
    }
  ],
  "declined": [{ "id": "eslint-prettier", "at": "2026-10-08T19:30:00.000Z" }]
}
```

| Field | Why it is there |
|---|---|
| `schemaVersion` | A future shape change is detectable; a manifest from another version is treated as unreadable, not misread. |
| `skill.name` / `skill.version` | Which skill wrote this, and at which version. The version is the skill's own (frontmatter `version:` or a `VERSION` file). |
| `appliedAt` | The last write, for a human reading the file. |
| `environment` | The detected stack the recipes were applied against. A later run can tell the ground moved (the package manager changed, a single package became a workspace) without re-deriving it. |
| `recipes[].id` | The recipe, by the same id the contract uses. |
| `recipes[].skillVersion` | The skill version at the moment *this* recipe was applied — a recipe applied under an older skill stays visible after the skill is updated. |
| `recipes[].recipeHash` | The recipe file's content hash at apply time. This is the recipe's **version**: it changes exactly when the recipe's output shape changes, and it cannot go stale the way a hand-maintained `version:` field can. |
| `recipes[].appliedAt` | Per-recipe, because recipes are applied one at a time and a failed verify leaves one unrecorded. |
| `recipes[].files[]` | The files the recipe wrote, with the action and the hash of the rendered content — the whole file for `create`, the marked block for `merge`. This is the ownership index the drift report needs. |
| `declined[]` | A decline is a decision, not an absence (see below). |

**The version question.** The ticket asks for "the skill and recipe version each was applied at".
The skill version is a real field. The recipe version is *not* a frontmatter field in the contract,
and a hand-maintained one goes stale the first time someone edits a recipe and forgets to bump it.
The prototype therefore records the recipe's **content hash** as its version. The alternative — add
`version:` to the recipe frontmatter and record it — is a contract change; the hash needs no
contract change and is strictly more precise. **Open for the human.**

## The precedence rule

**The filesystem wins.** The manifest is an index of what the skill wrote, never a claim about what
is true. Concretely:

- `classify()` reads the filesystem for presence and content. It consults the manifest for exactly
  one fact the filesystem cannot supply: *which bytes the skill wrote last time* (the recorded
  hash). A file that matches the current render could have been written by hand; only the manifest
  can say the skill wrote it.
- A manifest entry whose file is **absent** is `missing` — the plan proposes reinstating it on
  approval. The manifest never makes an absent file count as applied.
- A manifest entry whose file was **hand-edited** is `drifted` — the plan shows the diff and applies
  only on approval. Drift is never silently overwritten.
- A manifest that is **absent, corrupt, or from another `schemaVersion`** degrades the report to
  "compare against the current library only" (`degraded: true`). Nothing breaks; the ownership index
  is simply gone, and every library recipe reads as `new`.
- The manifest is **never written from the filesystem**. It is written only by an apply, one recipe
  at a time, after that recipe's verify passed.

This is the ADR `docs/adr/0001-filesystem-is-the-source-of-truth.md` made executable.

## What a `merge` entry owns

A `merge` entry owns only *part* of a shared file, and the contract has two kinds
(`RECIPE-CONTRACT.md`):

| Kind | Owned content | Example |
|---|---|---|
| `markers` | the marker-delimited block (`code-quality:<id>:start` … `:end`) | `.husky/pre-commit`, `.gitignore` |
| `json` | the leaf keys the fragment names, recursively | `package.json`, `tsconfig.json` |

The manifest hashes the **owned content**, never the whole file. This is the difference between a
useful ownership index and a useless one: `package.json` is shared with the project, so hashing the
whole file would report drift the moment the user adds an unrelated dependency. The decisive case —
an unrelated edit elsewhere in `package.json` stays `intact`, an edit to the recipe's own key reads
`drifted` — is in the transcript and in the demo's walkthroughs.

## The verdicts

Per file, from the recorded hash, the present content, and the current render:

| Verdict | Condition | What the plan does |
|---|---|---|
| `intact` | present and byte-identical to what the library would write now | nothing |
| `update` | present, untouched since apply, but the library's render changed | report the library-side re-render; apply on approval |
| `drifted` | present but hand-edited since apply (an update may also be pending — `updateAvailable`) | show the diff; never overwrite without approval |
| `missing` | absent, or (for a `merge`) its marked block is gone | reinstate on approval |

Per recipe, the worst file verdict wins (`missing` > `drifted` > `update` > `intact`). A recipe the
manifest does not know is `new`; one the library no longer selects is `stale`; one the user declined
is `declined`.

## The update path

A re-run is the same `classify()` call with the current library:

- `new` recipes are proposed for apply.
- `intact` recipes are reported as already applied — the no-op.
- `update` recipes are reported as a **library-side re-render**, not drift: the file is untouched,
  the recipe changed. This is the distinction the recorded `recipeHash`/file hash buys.
- `drifted` and `missing` recipes are reported with their diff, and applied only on approval.
- `stale` recipes (in the manifest, no longer selected) are reported for removal, never removed
  silently.

## Partial application

- A recipe the user **declined** is recorded in `declined[]` with the date. A re-run reports
  "previously declined" and asks again — it neither silently re-proposes it as `new` nor silently
  skips it.
- A recipe whose **verify failed** is not recorded at all (per the invocation-surface decision), so
  a re-run resumes there.
- A recipe is **atomic**: a decline is per recipe, not per file. Declining one of a recipe's files
  is not representable, and the prototype does not pretend otherwise.

## What it proved

**The real fixture run** (`prototype/manifest-transcript.mjs` → `prototype/manifest-transcript.txt`,
8 scenarios, 18/18 checks, exit 0, re-run byte-identical). A scratch Bun/TypeScript package, the
real `biome-assist` and `tsconfig-strict` recipes, the real templates:

| # | Scenario | Result |
|---|---|---|
| 1 | First apply | manifest written; every file `intact` |
| 2 | Re-run | every file `no-op (identical)`; nothing rewritten |
| 3 | Hand-edit `biome.json` | `drifted`; the edit survives — not overwritten |
| 4 | Unrelated `package.json` edit, then the recipe's own key | `intact`, then `drifted` — per-leaf ownership |
| 5 | `rm tsconfig.json` | `missing`, then reinstated on approval → `intact` |
| 6 | Bump a template | `update`, not drift (`presentHash === recordedHash`, `currentHash` differs) |
| 7 | Decline a recipe | `declined`; a re-run says "previously declined" |
| 8 | `rm .code-quality.json` | `degraded`; every recipe `new` |

**The shareable demo** (`prototype/manifest-demo.html`) drives the same module in an in-memory
world: 7 walkthroughs, 35 steps, every step changes the state panel, no page errors. It is the
artifact to click through; the transcript is the proof.

**A finding the transcript forced.** Scenario 6 bumps a *template*, and `recipeChanged` stays
`false` — the recipe's `.md` hash does not cover its templates. So `recipeHash` is only a coarse
"which recipe revision" marker; the **per-file recorded hash** is the authoritative update signal.
If the recipe version is meant to answer "did this recipe's output shape change", it must cover the
templates too (or be dropped in favour of the per-file hashes). **Open for the human.**

## Open questions for the human

1. **Recipe version: content hash or a `version:` frontmatter field?** The prototype uses the hash.
   And the hash must cover the recipe's **templates**, not just the `.md` — scenario 6 shows a
   template-only change leaves the `.md` hash untouched.
2. **`declined[]` — keep it, or let a decline be a plain absence?** Keeping it means a re-run can
   say "you declined this before"; dropping it means a re-run re-proposes it as new every time.
3. **Does the manifest belong in the skill's own drift report at all, or is it purely an
   optimization the plan may ignore?** The ADR says optimization; the prototype makes the plan
   *better* with it (it can say "the skill wrote this" and "the library changed") and correct
   without it.
